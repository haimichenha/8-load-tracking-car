## 当前 MCU 实现

当前 `LineFollowMissionDebug` 已增加 `bsp_car_pose_link.*`：

1. UART4（PC11 MCU RX）以 115200 8N1 单向读取 Pi 的原始 V2.3 字节流；当前也兼容读取
   旧本地 `FA...AB` 14 B 帧。当前物理构型没有 MCU -> Pi 回传控制链路，MCU 不向 Pi
   发送 `0x83`、`0x85` 或 ACK；
2. 首选输入为 `AA 55 02 80 31 32 ...`、22 B payload、CRC16/CCITT-FALSE 正确的帧；
3. 要求 `CoordinateFrame=FIELD_GLOBAL(0x01)`、`POSITION_VALID` 与 `YAW_VALID` 均置位、
   yaw 在 ±180.0° 内；速度无效时 `Vx=Vy=0x7FFF` 且清 `VELOCITY_VALID`，
   速度有效时两个字段都不得为 `0x7FFF`。Pi 输入应保持 `CALIBRATED=0`、
   `CalibrationId=0`；即使上游遗留该标记，MCU 也不以它作为校准权威。重复/乱序
   `SourceTimeMs` 不更新原始状态；
4. 仅对接收年龄不超过 250 ms 的样本，以车端地址 `0x30` 和广播目的 `0x10` 重编码为
   33 B `CAR_POSE`，每 100 ms 发送一次。LoRa 出口的 X 先减固定 `13 cm`，
   再镜像 X/Y、后叠加校准：
   `X_lora=-(X_pi-13 cm)+DeltaX`、`Y_lora=-Y_pi+DeltaY`、`yaw_lora=yaw_pi`；
5. MCU 根据实际循迹状态写入或清除 `CAR_RUNNING`，保留原始 Pi 坐标、yaw、速度和
   `SourceTimeMs` 供内部使用；仅在出站帧覆盖 `CALIBRATED/CalibrationId`。PG13/PG9
   先启动本地任务，连续三帧原始位姿有效且 MCU 本地校准有效后才通过 UART5 发出
   `CAR_TASK_REQUEST(0x81)`；运行中 PG13/PG9 二次按键发送 `MISSION_ABORT(0x84)`。
   `CALIBRATION_SET(0x83)` 由 MCU 本地应用后直接回复地面站；PG12 的
   `MAINTENANCE_RESET(0x85)` 直接清除 MCU 本地状态后广播。旧 14 B 兼容流没有 Pi
   时间戳，使用独立的 MCU 转发 epoch。

当前路线本地参考：A=`(0.0,0.0) cm`、B=`(-151.3,-8.1) cm`、C=`(-165.7,150.7) cm`、
D=`(-16.5,164.2) cm`。A/B 航向约 `0°`，C/D 航向约 `180°`；现场 `0x83` 校准后才可
把它们映射为当日 FIELD_GLOBAL。它们仅作雷达辅助，
车辆循迹主判据仍是灰度、JY901 yaw/yaw-rate 和编码器累计路径距离。

## Pi 单向原始位姿输入要求

Pi 只需在 UART4 连接的 TX 线上按 10 Hz 发送原始雷达参考坐标。它不接收 MCU 指令，
不保存 `DeltaX/DeltaY/CalibrationId`，也不响应 `0x83/0x85`。当前 MCU 在 LoRa
出口承担固定 X 偏移、镜像和本地校准时，Pi 不得重复任一变换；MCU 先对 X 减
`13 cm`，再对 X/Y 取反，最后叠加校准偏移：

```text
V=02 Type=80 Src=31 Dst=32 Seq=递增 Flags=00 Len=16(hex)
Payload:
  CoordinateFrame=01
  PoseFlags: POSITION_VALID|YAW_VALID；CALIBRATED 清零
  CalibrationId: 0
  X/Y: 原始 FIELD_GLOBAL 雷达参考，i32 big-endian，cm
  Yaw: i16 big-endian，0.1 度，逆时针为正
  Vx/Vy: 有效则 i16 cm/s；无效则均为 0x7FFF 且清 VELOCITY_VALID
  SourceTimeMs: Pi 单调毫秒，u32 big-endian
CRC16/CCITT-FALSE: 覆盖 Version 至 Payload，CRC 高字节先发。
```

历史 14 B `FA...AB` 雷达帧可用作当前硬件的迁移输入。MCU 将它视为原始位姿；
只有在本地 `0x83` 已生效时，出站帧才携带 `CALIBRATED=1` 和本地
`CalibrationId`。它不含 CRC、速度有效性和 Pi 时间戳，正式任务仍优先使用前述
22 B 输入格式。

## 验收顺序

1. 恢复并 SSH 验证雷达 Pi，确认其 UART4 发射端连接到 `PC11` 且无其他设备占用。
2. 静止 A 点：地面站连续收到 10 Hz `CAR_POSE`；检查 `src=0x30,dst=0x10,len=22`、CRC=0、
   `CAR_RUNNING=0`、新鲜度小于 250 ms。
3. 执行起飞前校准：先记录一帧未校准的出站 `CAR_POSE`，再发送 `0x83`；确认 MCU
   直接 ACK，随后至少三帧出站位姿为 `CALIBRATED=1`、固定非零
   `CalibrationId`，且 X/Y 相对校准前的增量等于 Delta。Pi 输入始终保持原始位姿。
4. 在 A 点按 PG13（任务一）或 PG9（任务二）低速循迹：地面站检查连续 10 Hz、
   `CAR_RUNNING=1`，而不允许无线 ACK 改变电机状态；PG10 不应产生事件。
5. 断开 Pi UART：250 ms 后不再发送 `CAR_POSE`；跑动中无线静默，静止后恢复维护 HEARTBEAT；
   留存 STM32 冻结日志与地面站统计。

无 Pi 的本地循迹是允许的：PG13/PG9 仍由灰度、JY901 和编码器启动和运行。它不能作为
无人机协同得分证据；Pi 后续恢复合格位姿时可延后建立协同会话。要计入正式空地任务，
必须留存 MCU 本地校准后的三帧位姿、`0x81`/ACK 和空侧预检证据，但这些不是车辆启动前置。

## 0x83 / PG12 维护联调（v2.3 正式闭环）

1. 地面站只在收到 `CAR_POSE.Seq mod 5=2` 后的 30–50 ms 维护窗口发送定向
   `CALIBRATION_SET(0x83, Src=0x40,Dst=0x30,ACK_REQUIRED,len=12)`。Payload 是
   `DeltaX(i32 BE), DeltaY(i32 BE), CalibrationId(u16!=0), APPLY=0x01, Reserved=0`。
2. MCU 只在 `CAR_RUNNING=0` 且本地未运行时接受 `0x83`，校验
   `Src=0x40,Dst=0x30,ACK_REQUIRED,len=12,CalibrationId!=0,APPLY=0x01,Reserved=0` 后，
   将 `DeltaX/DeltaY/CalibrationId` 写入 MCU RAM。它在下一 0–25 ms 小车时隙直接回
   地面站 `ACK(Src=0x30,Dst=0x40,RequestSeq=地面站 Seq,ACK_ACCEPTED)`，不转发给 Pi，
   也不等待 Pi ACK。重复 `Src+Type+Seq` 请求按 5 s 去重；停车状态下新请求 Seq 可覆盖
   当前 MCU 本地校准，`DeltaX/DeltaY` 始终相对原始 Pi 坐标完整替换，绝不累加。
3. 成功后，MCU 的下一批出站 `CAR_POSE` 必须是 `FIELD_GLOBAL`、
   `CALIBRATED=1`、固定的非零 `CalibrationId`；连续三帧相对校准前出站帧的 X/Y
   增量必须等于本次 `DeltaX/DeltaY`。MCU 只在出站阶段计算校准坐标，内部原始 Pi/radar
   坐标不变。
4. PG12 为低有效物理维护键。短按、行驶中按下或停车不足 12 s，均不得产生 LoRa `0x85`。
   合格长按由 MCU 立即清除本地 Delta、`CALIBRATED` 和 CalibrationId，并在连续三个小车
   时隙广播 `Src=0x30,Dst=0x10,Type=0x85,len=8`；三帧 ResetId、Seq、payload 相同，
   后两帧仅加 `RETRANSMISSION`。它不访问 Pi，无线侧也不等待 ACK。

5. 调试重校准不必先按 PG12：保持停车，使用新的 `0x83` 请求 Seq 和新的 CalibrationId。
   若要验证校准前后差分，`X_after-X_before=DeltaX_new-DeltaX_old`，
   `Y_after-Y_before=DeltaY_new-DeltaY_old`；未记录旧 Delta 时只验证新 ID、ACK 和三帧输出。

## 2026-07-30 UART4 实测修复

旧的 UART4 前台轮询会在 UART5 LoRa 发送或诊断输出期间错过 115200 baud 的 Pi 字节，造成
`FA...AB` 旧桥接帧偶发失步，进而让地面站的 CAR_POSE 新鲜/失效状态切换。现已改为
`UART4_IRQHandler` 的 256 B 单生产者/单消费者接收环形缓冲；控制循环只从该缓冲解析帧。

静止小车、刚下载后的两次 COM13 `P` 状态回读为：

```text
t=13104 ms: raw=3668, legacy_ok=262, legacy_bad=0, uart_err=0, ring_ovf=0,
             x=6 cm, y=8 cm, yaw=9.5 deg, age=37 ms
t=18347 ms: raw=5138, legacy_ok=367, legacy_bad=0, uart_err=0, ring_ovf=0,
             x=6 cm, y=8 cm, yaw=9.6 deg, age=29 ms
```

即当前线上的原始帧为 `FA 00 00 00 06 00 00 00 08 00 00 00 60 AB`，按既有 14 B 协议解码就是
`(X,Y,yaw)=(6 cm,8 cm,9.6 deg)`，并非 MCU 大端重编码产生的大数。原点零位在本实测下仅有数厘米的
静止残差；原始 Pi/radar 输入不在 MCU 内部擅自平移。需要现场坐标对齐时，地面站使用
`0x83` 让 MCU 仅在 LoRa 出站阶段应用 Delta，并保留原始输入供循迹辅助。

### 冷启动 source-time 回归

旧 14 B 兼容流缺少 Pi 的 `SourceTimeMs`。若直接使用 MCU boot uptime，而雷达在 MCU 上电较久后才开始
输出，地面站会把低于上一会话的时间视为过期帧，即使 UART4 与 LoRa 都在持续工作。

现兼容路径从**第一个有效旧帧**开始独立的转发 epoch（随后按实际接收间隔递增）。这只解决地面站的重启
序判定，不伪称为 Pi 时间。冷启动后 MCU 状态为 `src_ms=16146, age=19 ms, legacy_ok=324,
legacy_bad=0, uart_err=0`；地面站在未重启状态下随即恢复 `car_age=0.000 s`，证明 source-time epoch
可跨 MCU 重启重新接入。

同一时刻 UART4 原始帧 `FA010001D8010000A70000027BAB` 解码为 `X=-472 cm,Y=-167 cm,yaw=63.5°`。
这是真实 Pi 桥接输入，不是 MCU/LoRa 载荷错误；雷达“上电置零”需在 Pi 雷达侧继续核对。
